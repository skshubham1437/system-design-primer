# Content guide

How to write and review the original content on this site (quiz questions, rubrics, glossary entries, summaries, chooser scenarios). The upstream README is not edited here; see [ROADMAP.md](ROADMAP.md) for what is planned.

## Process

1. **Draft** from a named source: a section of this site or a cited primary source. Note the source in the pull request.
2. **Self-check** every claim against that source.
3. **Open a content-only pull request.** Do not mix content and code.
4. **Review** by someone who did not write it, using the checklist below.
5. **Merge.** Strict builds validate the file format; the reviewer validates the substance.

If a reviewer corrects more than one item in twenty, stop writing new content and fix the process first (clearer source notes, smaller batches).

## Reviewer checklist

- [ ] The answer is correct, and I verified it against the linked section or a primary source.
- [ ] Exactly one choice is defensible; the wrong ones are plausible but clearly wrong for a stated reason.
- [ ] The explanation says *why*, not just *what*, and its link lands on the right heading.
- [ ] No trick wording. It tests understanding rather than trivia.
- [ ] Numbers and claims are cited; archived copies are used when originals are gone.
- [ ] Plain language; terms are defined or in the glossary.
- [ ] Original wording; nothing copied from copyrighted sources.

## Style

- Short sentences. Prefer concrete numbers and scenarios to abstractions.
- Name the trade-off. "Faster, but …" is more useful than "fast".
- One idea per question or definition.
- No emoji, no jokes at the learner's expense, no "obviously".

## Where each kind of content lives

| Content | File | Checked by |
|---|---|---|
| Quiz questions | `content/quizzes/<topic>.yaml` | `scripts/validate/quizzes.mjs` |
| "Try it first" rubrics and follow-ups | `content/practice/<solution>.yaml` | `scripts/validate/practice.mjs` |
| Decision aids | `content/choosers/<id>.yaml` | `scripts/validate/choosers.mjs` |
| Interactive pages (labs) | `content/labs/<slug>.md`, listed in `scripts/site-map.mjs` | strict build (links) |
| Sections added to an upstream page | `content/extras/<page-slug>.md` | strict build (links) |
| Dead-link replacements | `data/link-overrides.json` | generated by `scripts/link-overrides.mjs` |

Each YAML file has `reviewed: false` until a second person has checked it. While it is false, learners see a "Draft" notice.

### Writing YAML safely

- **Put every sentence in double quotes.** An unquoted line containing a colon and a space (for example `I described the read path: look it up`) is read as a nested object, not text. The validators will catch it, but quoting avoids it. Avoid double quotes inside the text; use single quotes or rephrase.
- Run `STRICT=1 npm run build` before opening a pull request. It checks the format, that every link and anchor resolves, and that nothing points at a section that no longer exists.
- Quiz and chooser answers must be defensible from the page they link to. If you cannot point at the sentence that supports an answer, the question is not ready.
